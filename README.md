# Meal Planner

Nuxt 4 app deployed to a self-hosted Coolify instance, using Supabase for the database and auth, Vuetify as the component library, and CSS Modules for page/layout structure.

## Setup

```bash
npm install
cp .env.example .env
```

Fill in `.env` with your Supabase project's URL, anon key, and service role key from the Supabase dashboard (Project Settings → API).

## Development Server

```bash
npm run dev
```

Runs on `http://localhost:3000`.

## Linting

```bash
npm run lint       # ESLint via @nuxt/eslint (config in eslint.config.mjs)
npm run lint:fix   # apply auto-fixes
```

Vue single-file components put `<script>` first, then `<template>`, then `<style>` (`vue/block-order`).

## Production

```bash
npm run build      # Nitro build for the node-server preset
npm start          # serve .output/server/index.mjs on port 3000
```

### Deploying on Coolify

1. Create a new application from this Git repository and choose the **Dockerfile** build pack.
2. Set the exposed port to `3000` and attach your domain (Coolify provisions TLS).
3. Add these environment variables as runtime variables:
   - `NUXT_PUBLIC_SUPABASE_URL`
   - `NUXT_PUBLIC_SUPABASE_ANON_KEY`
   - `NUXT_SUPABASE_SERVICE_ROLE_KEY` (mark as secret, never expose to the client)
   - `NUXT_GEMINI_API_KEY` (mark as secret; protein swaps, see "Protein swaps") and optionally `NUXT_GEMINI_MODEL`
4. Enable the Git webhook for automatic deploys.

Place the Coolify server in the same region as the Supabase project to keep SSR auth/DB calls fast.

## Database migrations

Keep every schema change as SQL in `supabase/migrations/` so the database can be replayed on any Supabase instance (managed or self-hosted). Avoid dashboard-only changes.

## Styling conventions

- **Vuetify** components (`v-btn`, `v-card`, form inputs, etc.) own look and feel.
- **CSS Modules** (`<style module>` in SFCs, or `Component.module.css` files) own page/layout structure — grids, containers, spacing wrappers.
- Shared design tokens live in `app/assets/css/tokens.css` (spacing, radii, breakpoints) and `app/assets/css/theme.css` (color custom properties). Colors are defined only in the `vuetify.vuetifyOptions.theme` block in `nuxt.config.ts`; Vuetify writes the active theme to `--v-theme-*` variables on `:root`, and `theme.css` aliases them as `--color-*` for CSS-Modules layout code. Add a new color to both themes in `nuxt.config.ts`, then alias it in `theme.css`.
- The theme preference is `light`, `dark` or `system`. Change it through `useProfileSettings().changeTheme()` (saves to the profile when signed in). `useAppTheme()` keeps it in a `theme` cookie that `app/plugins/theme.ts` applies during the server render; for `system` the server uses the OS theme the browser last reported (`theme-system` cookie), so Vuetify's `:root` variables already match and there is no flash of the wrong theme.

## Auth

Auth uses Supabase's `@supabase/ssr` cookie-based session pattern:

- `server/middleware/supabase.ts` creates a per-request Supabase server client, refreshes the session, and exposes it via `event.context.supabase` / `event.context.supabaseUser`.
- `app/plugins/supabase.client.ts` creates the browser client and keeps `useSupabaseUser()` in sync via `onAuthStateChange`.
- `app/middleware/auth.global.ts` runs on every route: signed-out users go to `/login`, signed-in users visiting `/login` go to `/`.
- `app/middleware/auth.global.ts` also treats `/forgot-password` as guest-only, and sends signed-out visitors of `/reset-password` to `/forgot-password`.
- `/login` has Sign in and Create account tabs (email + password), a "Forgot password?" link and a "Continue with Google" button. Supabase errors are mapped to translation keys in `app/utils/getAuthErrorKey.ts`.
- `/forgot-password` sends a Supabase reset email; `/reset-password` sets the new password once the reset link has signed the user in.
- Every auth screen honours `?next=<same-origin path>` (validated by `shared/utils/getSafeNextPath.ts`): the auth guard sends signed-out visitors of `/join/<token>` to `/login?next=/join/<token>`, and sign-in, sign-up and Google sign-in all return to it.
- `server/routes/auth/callback.get.ts` finishes Google sign-in and reset links by exchanging the PKCE code for a session cookie, then redirects to the `next` path (same-origin only; default `/`).

Supabase project settings this app expects:

- **Confirm email must stay off** (Authentication → Sign In / Providers → Email). Sign-up then returns a session and the user lands on the home page straight away.
- **Google provider** must be configured before "Continue with Google" works; see [docs/google-sign-in-setup.md](docs/google-sign-in-setup.md).
- **Password reset** needs `/auth/callback**` redirect URLs, the bilingual reset email template and, for production, Mailgun as custom SMTP; see [docs/password-reset-setup.md](docs/password-reset-setup.md).

## Profile

- `profiles` has one row per auth user, created by the `on_auth_user_created` trigger (`supabase/migrations/20261021000000_create_profiles.sql`). The display name comes from Google's `full_name`/`name`, else the part of the email before `@`. `locale` starts empty and is set to the language the user first browses in.
- RLS: a user reads and updates only their own row (`display_name`, `locale`, `theme`, `diet` columns only); members of the same household can read it through `shares_household()`, so they can see each other's diet. Inserts happen only through the trigger, deletes through the `auth.users` cascade.
- `app/plugins/profile.ts` loads the profile during SSR and whenever the signed-in user changes, then applies its theme and language over the cookies. `useProfile()` reads and saves the row; `useProfileSettings()` applies a change at once and puts the old value back if saving fails.
- `/me` edits the display name, language and theme, links to Household and Food preferences, and holds sign-out.
- `/me/preferences` (Food preferences) holds the diet picker and "My meal ratings" (C4, see "Recipe ratings"), the user's rated recipes in one tab per rating.

### Diet

- `profiles.diet` is one value per user, `full` by default (`supabase/migrations/20261027000000_add_profile_diet.sql`). The check constraint `profiles_diet_supported` lists the six values; `DIETS` in `shared/utils/diet.ts` must match it. The migration only adds a column, so run it before deploying the app version that reads it.
- The ladder is written once, as `DIET_LADDER` in `shared/utils/diet.ts`. Each step lists the proteins it adds and a diet allows its own step and every step before it, so `allowedProteins(diet)` and `isProteinAllowed(diet, protein)` are derived and the steps cannot drift out of order. Recipes are tagged with the same `PROTEINS` (D1, see "Recipe proteins").

  | Diet | Adds | Allows |
  | --- | --- | --- |
  | `vegetarian` | egg/dairy, plant | egg/dairy, plant |
  | `fish` | fish | the above + fish |
  | `poultry` | poultry | the above + poultry |
  | `pork` | pork | the above + pork |
  | `beef` | beef | the above + beef |
  | `full` | other meat (lamb, game, offal) | everything |

- To add or reorder a step: edit `DIET_LADDER`, add a migration that replaces the constraint, and add the `profile.diet.options.<diet>` translations in both locale files.

## Households

- `households` and `household_members` (one row per member). `household_members.user_id` is unique, so a user belongs to one household. `household_members.role` is `owner` or `member`; a partial unique index allows one owner per household. Households that existed before B3 (`supabase/migrations/20261026000000_add_household_member_management.sql`) got their earliest member as owner.
- `create_household(household_name)` (`supabase/migrations/20261021000100_add_household_creation.sql`, owner added in the B3 migration) is the only way to create a household; the creator becomes its owner. It trims and checks the name (1–50 characters), writes the household and your member row in one transaction, and raises `already_in_household`, `invalid_household_name` or `not_authenticated`. The tables have no insert policies, so direct inserts are denied.
- `useHousehold()` loads your household and its members in one query (member names come through the `household_members.user_id` to `profiles.id` foreign key) and creates one through the function. `app/plugins/household.ts` forgets the loaded household when the signed-in user changes.
- `/household` shows the create form or the household overview. The Home page has a household card and `/me` a Household row.
- Invites (`supabase/migrations/20261023000000_add_household_invites.sql`): any member can create a link for their household (`create_household_invite()`), which works once and for 7 days, and revoke it (`revoke_household_invite()`). There is one live link per household: creating a new one revokes the old one. Only the SHA-256 hash of the 192-bit token is stored, so the URL is shown only right after it is created; the invite card on `/household` shows status, expiry and Revoke afterwards. `household_invites` has no write policies and its `token_hash` column is not readable.
- `/join/<token>` previews a link with `get_household_invite()` (valid, expired, revoked, used or not found) and joins with `accept_household_invite(token, leave_current)`. A user who is already in another household chooses between staying and leaving it for the new one; leaving removes them from the old household, which is deleted if they were its last member. The whole switch is one transaction, and concurrent use of one link is serialised by a row lock, so the second user sees "already used".
- Member management (B3, same migration as the role): `remove_household_member(user)` (owner only; also revokes the invite links that person created), `leave_household()`, `transfer_household_ownership(user)` and `delete_household()` (owner only). All lock the household row first, so they take turns, and raise `not_owner`, `owner_must_transfer`, `member_not_found`, `cannot_remove_self`, `invalid_new_owner` or `not_in_household`. An owner with other members cannot leave, and cannot switch households through an invite: they transfer ownership or delete the household first. The last member leaving deletes the household. `/household` shows a menu on each other member's row for the owner, a Leave button and, for an owner with company, Delete household.
- `AppNavigation` (mounted in `app/layouts/default.vue`) is the bottom bar on phones and a side rail from 960 px. List is disabled until its page exists: give its entry in `NAV_ITEMS` a `to` when it does.

## Meal plans

- `meal_plans` (`supabase/migrations/20261106000000_create_meal_plans.sql`, E1) has one row per plan: `kind` is `individual` (`user_id` set, readable and changeable by that user only) or `household` (`household_id` set, for every member of that household). `start_date` is a `date`, `day_count` is 1 to 14, `created_by` is kept for history (set to null if that account is deleted). Deleting a household deletes its plans; deleting an account deletes that user's individual plans; leaving a household ends access to its plans at once.
- `meal_plan_slots` has exactly one row per day and meal type (`unique (plan_id, day_index, meal_type)`); a slot's date is `start_date + day_index`. `recipe_id` is filled by hand (E3) or by the generator (E4); deleting a recipe empties its slots.
- `create_meal_plan(plan_kind, plan_start_date, plan_day_count, plan_include_snacks, plan_snacks_on_list)` is the only way to create a plan. It writes the plan and all `day_count × 4` slots in one transaction and returns the plan id. A household plan is always for the caller's own household (the client never sends one). It raises `not_authenticated`, `invalid_plan_kind`, `invalid_start_date`, `invalid_day_count` or `not_in_household`. The tables have no insert or delete policies.
- `meal_plan_participants` (`supabase/migrations/20261107000000_add_meal_plan_participants.sql`, E2) lists who eats from each plan, one row per `(plan_id, user_id)`; quantities scale to their number (`getPlanServings` in `shared/utils/mealPlan.ts`). An individual plan's only participant is its owner. A household plan starts with every current member unless `create_meal_plan(…, plan_participant_ids)` names some, and `set_meal_plan_participants(target_plan_id, participant_ids)` replaces the set later (and moves `meal_plans.updated_at`). Both allow current members of the plan's household only and at least one participant (`no_participants`, `participant_not_member`; `participants_not_allowed` for an individual plan, `plan_not_found` for someone else's). Rows are readable with their plan and have no insert, update or delete grants. A member who leaves or is removed is taken off that household's plans by a trigger, which can leave a plan with no one in it; the plan page then asks who eats from it.
- Snack options: `include_snacks = false` skips snack slots (the rows stay, hidden, so switching back loses nothing) and `snacks_on_list = false` leaves snack ingredients off the shopping list (G2 reads it). They are the only columns that can be updated (`grant update (include_snacks, snacks_on_list)`), by whoever can read the plan.
- Slot editing (E3, `supabase/migrations/20261108000000_add_meal_plan_slot_editing.sql`): `set_meal_plan_slot(target_slot_id, new_recipe_id, fill_days = 1)` is the only way to change a slot. It needs access to the plan (`plan_not_found` otherwise), a recipe of the slot's meal type (`recipe_not_found`, `meal_type_mismatch`), and `fill_days` from 1 to the recipe's `portion_days` (`invalid_fill_days`); `fill_days = 2` also puts the recipe in the same meal on the next day, both or neither, and a batch may not run past the plan's last day (`beyond_plan_end`). A null recipe empties that one slot. It locks the plan row and moves `updated_at`. A batch is not stored as a link: the same recipe in consecutive slots is the batch.
- `meal_plan_hated_recipes(target_plan_id)` returns `(recipe_id, user_id)` for every recipe a current participant rated `hate`, and nothing for a plan the caller cannot open. It is the one exception to private ratings: only `hate`, only the plan's participants, only to people who can see the plan, so the picker can say "Monika marked this as hate". `supabase/tests/meal_plan_slots.test.sql` covers both functions.
- On `/plans/<id>` every visible slot is a button that opens the slot picker (`PlanSlotPicker` + `PlanSlotPickerPanel`): a bottom sheet below 960 px, a dialog above. It lists the recipes of the slot's meal type from the cached recipe library, with a search that ignores case and accents, the current choice first, a red line for recipes a participant hates (still choosable), and "Clear slot" for a filled slot. Choosing a 2-day recipe when the next day is in the plan asks "Only Tue" or "Tue + Wed", and names a next-day recipe it would replace. The rules are pure in `shared/utils/slotPicker.ts`. The page changes at once and puts the old slots back if the save is refused; a filled slot with a hated recipe shows a warning icon in the week list.
- `/plans` lists your plans in sections (see "Plan overview and history"), `/plans/new` creates one (household or just me, start date defaulting to next Monday on the user's own clock, 1 to 14 days, participants with everyone ticked for a household plan, snack options, workdays and cooldown; "Create empty" or "Generate plan"), and `/plans/<id>` shows the week (a day list on phones, a grid from 960 px) with the participants (household plans) and the snack switches, which save at once. Someone else's plan reads as "not available". Day arithmetic is in `shared/utils/mealPlan.ts` on `YYYY-MM-DD` strings in UTC, so dates never shift with time zones.

### Plan generation

"Generate plan" on the New plan screen creates the plan and fills it; on `/plans/<id>`, "Generate plan" (nothing chosen yet) or "Fill empty slots" fills the empty slots the plan shows, "Regenerate unlocked" replaces every recipe that is not locked, and "Suggest another" in the slot picker swaps one slot (see "Lock, swap, regenerate"). No AI is called.

- The rules are a pure, deterministic module, `generateMealPlan()` in `shared/utils/planGenerator.ts` (types in `planGenerator.types.ts`, seeded random in `seededRandom.ts`), with unit tests on fixed seeds. In priority order:
  1. **Diet** (never relaxed): a recipe fits every participant's diet (`isRecipeCompatible()`), or a `ready` protein swap exists for each diet it breaks (D2's stored swaps only; nothing is generated). Such a recipe has half the weight.
  2. **Preferences**: a recipe any participant hates is never planned (never relaxed). Each participant who enjoys it adds the base weight once more (one fan doubles it); each "enjoy less" halves it. A liked recipe is likelier, never certain.
  3. **Cooldown**: a recipe planned in another plan of any participant (household or individual) within `cooldown_days` before the start rests, liked ones too; afterwards its weight recovers evenly from half to full over the same number of days.
  4. **Workday batches**: lunch and dinner are laid out first as 2-day spans where they save cooking on the plan's `workdays` (cook on day N, eat on N and N+1): Mon–Sun with Mon–Fri workdays becomes Mon–Tue, Wed–Thu, Fri–Sat and Sun; a week starting on Saturday becomes Sat, Sun–Mon, Tue–Wed, Thu–Fri. Batches are filled before anything else, with `portion_days = 2` recipes.
  5. **Variety**: a recipe is planned at most once per started week of the plan (a batch counts once), never on the next day in the same meal, and the same meat or fish twice in a day has half the weight.
- When a slot cannot be filled by the rules they relax in steps, instead of leaving it empty: a resting recipe comes back (least recently used first, noted `recently_planned`), then a recipe this plan already has (least used first, `repeated_in_plan`). A batch span relaxes the rest before giving up its batch (workdays first: there are only 17 batch recipes), never repeats a batch within the plan, and otherwise becomes two single days (`no_batch_recipe` on workdays). A slot with no recipe that fits the diets (`no_recipe_fits_diets`) or that no one hates (`all_recipes_hated`) stays empty. The note is stored in `meal_plan_slots.fill_note`, shown under the slot, and cleared when the slot is chosen by hand.
- `POST /api/plans/<id>/generate` (`server/api/plans/[id]/generate.post.ts`) runs `generatePlan()` (`server/utils/planGenerationService.ts`, tested with an in-memory store). It reads the plan with the user's own client, so RLS decides whether they may open it (404 otherwise), then, with the service role, the participants' diets and ratings and their plan history (twice the cooldown back), and writes the result as the user with `apply_meal_plan_generation()`. It answers `200 {status: "generated", filledCount, emptyCount, compromisedCount, seed}` or `409 {status: "nothing-to-fill" | "no-participants" | "plan-changed"}`. Every generation logs its seed as a JSON line; sending `{seed}` in the body reproduces it.
- Database (`supabase/migrations/20261109000000_add_meal_plan_generation.sql`): `meal_plans.workdays` (ISO weekdays, Monday = 1, default Monday to Friday) and `meal_plans.cooldown_days` (0 to 60, default 14) are chosen when the plan is created (`create_meal_plan(…, plan_workdays, plan_cooldown_days)`, raising `invalid_workdays` or `invalid_cooldown_days`) and are not updatable yet. `apply_meal_plan_generation(target_plan_id, assignments)` checks access, meal types and recipes like `set_meal_plan_slot()`, writes only into slots that are still as the server read them (`plan_changed` refuses the whole generation otherwise, and the page reloads the plan; E4 wrote into empty slots only, E5 below), and moves `updated_at`. `meal_plan_generation_participants()`, `meal_plan_participant_ratings()` and `meal_plan_recipe_history()` are executable by the service role only. `supabase/tests/meal_plan_generation.test.sql` covers them. The migration is additive and can run before the deploy.
- The plan page marks the plan's workdays ("Workday") and shows batches as "Day 1 of 2 · covers Wed" / "Day 2 of 2 · cooked Tue" (`getBatchDays()` in `shared/utils/slotPicker.ts`).

### Lock, swap, regenerate

- A slot is locked or not (`meal_plan_slots.is_locked`, E5, `supabase/migrations/20261110000000_add_meal_plan_slot_locks.sql`). A recipe chosen by hand is locked, on every day it fills (`set_meal_plan_slot()`); an emptied slot and a generated recipe are not. A slot counts as locked only while it holds a recipe, so one whose recipe was deleted is open again. Slots filled before the migration start locked, as E4 kept them so; this runs only when the column is first added.
- The lock icon on a filled slot locks or unlocks it with `set_meal_plan_slots_locked(target_slot_ids, should_lock)`: slots of one plan the caller can open (`plan_not_found`, `invalid_slots`), filled to be locked (`slot_empty`). The page sends both days of a batch (`getBatchSlots()` in `shared/utils/slotPicker.ts`), so a batch locks and unlocks as one. It locks the plan row and does not move `updated_at`.
- `POST /api/plans/<id>/generate` takes `{mode}`: `fill_empty` (the default, E4's behaviour) keeps every filled slot; `regenerate_unlocked` replaces every unlocked one the plan shows and answers `409 {status: "all-locked"}` when none is left. "Regenerate unlocked" floats above the navigation on phones and sits beside the title from 960 px; it shows while there is a filled, unlocked slot.
- `POST /api/plans/<id>/slots/<slotId>/swap` (`swapPlanSlot()` in `server/utils/planGenerationService.ts`) runs the same generator on that slot only, with every other slot kept and the slot's current recipe left out (`excludedRecipeIds`), so the new one differs and obeys the same rules (diet, hate, cooldown, variety against the rest of the plan, workday batches). The days of a batch are swapped together; a day someone locked stays. It answers `200 {status: "swapped", …}` or `409 {status: "slot-locked" | "no-alternative" | "no-participants" | "plan-changed"}`; nothing is written when no other recipe fits. An empty slot gets a suggestion the same way ("Suggest one"). The picker stays open on the new choice, so the user can swap again; a locked slot offers no swap until it is unlocked (choosing by hand still works).
- `apply_meal_plan_generation()` now also replaces recipes: each assignment names the recipe the server read for that slot (`previous_recipe_id`; missing means empty, as E4's app sent), and the whole write is refused with `plan_changed` when a slot holds something else by then or is locked. Written slots are unlocked. `supabase/tests/meal_plan_slot_locks.test.sql` covers the lock, the hand-pick lock and the write rules.

### Plan overview and history

- `/plans` (E6) has three sections on the viewer's own date (`useToday()`): **Current** (running today, with "day 3 of 7"), **Upcoming** (starting later, soonest first) and **Past** (ended, newest first, ten at a time with "Show older plans"). The home card shows the current plan, else the next one, else the latest (with E7, one the viewer eats from first, see "Plans side by side"). Both read one overview (`useMealPlanOverview()`, `loadOverview()` / `loadPastPlans()` in `useMealPlans()`), filtered by `meal_plans.end_date` (`supabase/migrations/20261111000000_add_meal_plan_end_date.sql`, a stored generated column, `start_date + day_count - 1`, indexed with the household or owner). `getPlanTimeline()` in `shared/utils/mealPlan.ts` gives current / upcoming / past.
- Visibility is E1's row level security, unchanged: every member of a household sees all its plans, past ones and those from before they joined included; an individual plan is its owner's alone; someone who leaves or is removed loses the household's plans at once. `supabase/tests/meal_plan_history.test.sql` covers the end date and the list's queries for each of them.
- The plan page's week (`usePlanWeek()` for both views): on phones a strip of days (`PlanWeekStrip`, today highlighted, a tap scrolls to the day) above the day list; from 960 px a grid of days across and meals down (`PlanWeekGrid`, weeks of seven, a two-week plan wraps), with the options below it. The days of a batch carry its tint (green, or amber for every other batch of a meal, from `batchNumber` in `getBatchDays()`): in the grid they are drawn as one joined block ("Cook · covers Wed", "Day 2 · cooked Tue"), in the list as a bar on the left. A day a batch starts on says "Cook tonight" (instead of "Workday"); the header says "Household plan · 3 people" and Current, Upcoming or Past.
- A past plan is read-only in the app: no picker, locks, generation, participant or snack changes, and a note says so. The database still allows those edits (the past is the viewer's date, which the server does not know).
- The slot picker has filter chips: **2-day batch**, **Enjoyed** (the viewer's own "enjoy" ratings only: everyone else's stay private), **Fits all diets** (every participant's diet allows the recipe without a swap; the household's member diets or, for an individual plan, the owner's) and **Not recent** (planned within the plan's cooldown before it starts, in plans the viewer can see that share a participant: `getRecentlyPlannedRecipes()`, the generator's rule without the plans the viewer cannot read; such a recipe says "Planned 2 Nov · cooldown"). The chips combine; the current choice always stays on top. The rules are in `matchesRecipeFilters()` (`shared/utils/slotPicker.ts`).

### Plans side by side

- A member who does not eat from a household plan for a week (E2 lets anyone untick them) can have their own plan for the same days (E7). Both are ordinary plans: `create_meal_plan()` never refuses plans that share days, and nothing ties the two together. Each keeps its own slots, participants and servings (`getPlanServings` per plan) and, when Epic G lands, its own shopping list (lists are keyed by plan). There is no migration; `supabase/tests/meal_plan_alongside.test.sql` covers making the plan after unticking yourself, who sees which plan, that neither plan's edits touch the other, that plans for the same days stay out of each other's generation history, and that leaving the household keeps the individual plan.
- The plan page reads the other plans the viewer can see that share a day with it (`loadOverlappingPlans()` in `useMealPlans()`, RLS decides) and `getPlanAlongside()` (`shared/utils/planAlongside.ts`) says what to show (`PlanAlongsideNotice`): on a current or upcoming household plan the viewer does not eat from, "Create my own plan", or "Open my plan" when they already have one for some of those days; on their own plan, the household plan beside it (a warning when they still eat from it too). Nothing is said on past plans. Unticking yourself shows the prompt at once.
- "Create my own plan" opens `/plans/new?kind=individual&start=<date>&days=<n>`: the household plan's days, or for a running plan the rest from today. `parseNewPlanQuery()` ignores anything missing or not allowed, so a hand-edited address opens the screen with its defaults; a household plan is offered only to someone in a household.
- The plan list says "Household plan · without you" for a household plan the viewer does not eat from. The home card prefers a plan the viewer eats from (`getFeaturedPlan()`): running before later, then any running or later plan; its hint names the kind ("Now: 9 – 15 Nov · Just me").
- The generator's cooldown still reads only days before a plan starts, so a household plan and an individual plan for the same days never rest recipes for each other: they feed different people that week.

## Recipes

- `/recipes` lists the recipes and `/recipes/<id>` shows one, for any signed-in user (no household needed). There is no schema change: `recipes` and `recipe_ingredients` are readable by `authenticated` through RLS and writable only with the service role (`supabase/tests/recipes.test.sql`).
- `pages/recipes.vue` is the parent route. It loads the whole list once (`useRecipes().loadList()`: ids, names, meal type and `portion_days` only, about 90 bytes a row) and filters it in the browser. Supabase caps a response at 1000 rows without an error, so the list is read in pages of `RECIPE_PAGE_SIZE` until the exact count is reached (`shared/utils/fetchAllPages.ts`); a library of several thousand recipes still loads whole. Past that, move the filter to the server (`meal_type` is indexed) and page the list. The filter is the `?meal=` query (`all`, `breakfast`, `lunch`, `dinner`, `snack`; anything else means `all`, see `shared/utils/mealFilter.ts`), so reload and the back button keep it, and opening a recipe carries it along.
- Below 960 px one pane shows at a time (the list, or the recipe with a back button). From 960 px the list sits on the left, scrolls on its own and stays while a recipe opens on the right.
- The detail shows ingredients per person's portion, in `position` order, as stored: amounts follow the active locale (`shared/utils/recipeAmount.ts`), units are the free text from the seed, and a missing amount reads "to taste". It also shows the instructions as one paragraph and a batch chip from `portion_days` ("1 day" or "N-day batch"). The list shows the chip only for batches. An empty ingredients or instructions section is not drawn (one seeded recipe has neither yet).
- Calories and macros are never selected with the list or the detail (`RECIPE_LIST_COLUMNS` and `RECIPE_DETAIL_COLUMNS` in `app/utils/recipe.ts`); they are read on their own once the user asks (see "Nutrition").
- Recipe names, ingredients and instructions are Lithuanian only until X1b adds translation tables; all other text is translated.

### Recipe proteins

- `recipes.main_proteins` (D1, `supabase/migrations/20261104000000_add_recipe_main_proteins.sql`) lists the proteins that decide whether a recipe fits a diet, from the `PROTEINS` vocabulary in `shared/utils/diet.ts`. The meat or fish in the dish is tagged (chicken pasta with cheese is `{poultry}`); `egg_dairy` or `plant` only when there is none. Several tags mean the dish has all of them (BLT is `{pork,poultry}`). When a recipe offers a choice of meat it is tagged with the option lower on the diet ladder, and an unspecified broth counts as vegetable.
- The column is `not null` with no default, and two checks keep it to a non-empty list of known proteins (`recipes_main_proteins_supported`, `recipes_main_proteins_not_empty`). A seed migration that adds recipes must set it. The D1 migration tags all 123 seeded recipes, grouped by protein with the judgment calls commented; it adds the non-empty check after tagging, so a recipe name that does not match aborts it.
- `isRecipeCompatible(diet, mainProteins)` in `shared/utils/diet.ts` is the one place that answers "does this recipe fit this diet": every main protein must be allowed by the diet. An empty list fits `full` only. `isProtein()` narrows a string from the database to a `Protein`. The ladder is not repeated in SQL; the plan generator (E4) filters by diet on the server.
- To add a protein: add it to `PROTEINS` (and a ladder step), then replace `recipes_main_proteins_supported` in a new migration.

### Recipe ratings

- A user rates a recipe `enjoy`, `enjoy_less` or `hate` (C3) from the detail (a three-way toggle under the title; tapping the active option clears it) or from a list row (the heart button opens a menu with the three values and Clear). Unrated is no row.
- `public.user_recipe_preferences` (`supabase/migrations/20261030000000_create_user_recipe_preferences.sql`) has one row per (`user_id`, `recipe_id`). The check constraint `user_recipe_preferences_rating_supported` lists the three values; `RECIPE_RATINGS` in `shared/utils/recipeRating.ts` must match it. The migration only adds a table, so run it before deploying the app version that reads it.
- RLS: the owner alone can read, add, change (`rating` only) and delete a row. There is deliberately no household policy, so even a household member cannot read a rating; the only exception is `meal_plan_hated_recipes()` (E3, see "Meal plans"), which returns the `hate` ratings of a plan's participants. The plan generator (E4) reads the participants' ratings on the server with the service role (`meal_plan_participant_ratings()`), after reading the plan as the user, and only turns them into weights (`supabase/tests/user_recipe_preferences.test.sql`).
- `useRecipeRatings()` holds the user's ratings in one shared map, loaded with the recipe list in `pages/recipes.vue`, so the list and the open recipe stay in step. `rate()` changes the screen at once and puts the old value back, with a message, if saving fails. If loading fails the controls are hidden and a warning is shown, so "unrated" is never shown falsely. The map is cleared whenever the signed-in user changes (`app/plugins/profile.ts`).
- "My meal ratings" (C4, `ProfileMealRatings.vue` on `/me/preferences`) joins that map with the cached recipe list in the browser (`groupRecipesByRating()` in `shared/utils/recipeRating.ts`), so it needs no query of its own. It has a tab per rating with its count; the tab is kept in the address (`?rating=hate`). A row's "⋯" button opens the same menu as the recipe list (`RecipeRatingMenu`, `trigger="more"`): picking another rating moves the row to that tab, Clear removes it. If either list fails to load a warning replaces the section, so "nothing rated" is never shown falsely.

### Protein swaps

A recipe a diet excludes gets an AI-proposed protein swap (D2): which ingredients to replace, with what, and how much. It is made **on demand** and stored, so each recipe and diet reaches the AI at most once.

- `GET /api/recipes/<id>/swaps/<diet>` (signed in) returns `200 {status: "ready", swap}`, `202 {status: "pending"}` with `Retry-After` while another request is generating it, `503 {status: "unavailable", retryAfter}` after a failed generation, or `404 {status: "not-needed"}` when the recipe already fits. A user may cause at most 20 new generations an hour (`server/utils/swapMissLimiter.ts`); stored swaps are never limited. D3 shows the swap. The plan generator (E4) only reads stored `ready` swaps and never asks for new ones.
- `getOrCreateSwap()` (`server/utils/proteinSwapService.ts`) is the one entry point. A stored `ready` swap made from the recipe's current ingredients (a hash of them, plus the prompt version) is returned as is. Otherwise the request claims the pair with `claim_recipe_protein_swap()` (one winner; others get "pending"), asks Gemini (`server/utils/ai/gemini.ts`, JSON mode with a response schema), validates the answer and saves it with `save_recipe_protein_swap()` in one transaction.
- The rules are pure in `shared/utils/proteinSwap.ts`: the prompt (recipe text only, never user data), the response schema, and `validateSwap()`. A swap must replace only ingredients at positions that exist in the recipe, label each with a protein the diet excludes, replace every excluded protein with one the diet allows, leave the recipe passing `isRecipeCompatible()`, give amount and unit together (at most 3x the original amount in the same unit), and not name an excluded meat or fish (plant-based imitations aside). An invalid answer is asked again with its errors; rate limits and server errors are retried with backoff; three attempts in all.
- Nutrition is the AI's estimate for the swapped recipe and always `nutrition_approximate = true`; an estimate outside 0.5x to 1.5x of the original calories (or negative, or incomplete) is dropped and the swap kept.
- `recipe_protein_swaps` (`supabase/migrations/20261105000000_create_recipe_protein_swaps.sql`) has one row per recipe, diet and locale (`lt` for now; X1c adds `en`) with `status` `pending`, `ready`, `failed` or `rejected`; `recipe_protein_swap_items` holds the replacements, each pointing at an ingredient of the same recipe. Signed-in users read `ready` rows only; only the service role writes. A failed pair is logged (one JSON line per generation) and retried by the next request after `retry_after` (5 minutes, then 1 hour, then daily). To throw a swap away, set its `status` to `rejected`: the next request regenerates it.
- The Gemini key is private runtime config (`NUXT_GEMINI_API_KEY`); without it stored swaps still load and new ones are `unavailable`. `NUXT_GEMINI_MODEL` defaults to `gemini-flash-latest`.
- Optional backfill, to spare the first viewers the wait: `npm run swaps:generate` asks for every conflicting pair through the same service (stored ones are skipped), writes `swap-review.md` to check by eye, and exits 1 if any pair is left without a swap. `-- --dry-run` lists the pairs and their status; `-- --recipe <id>` and `-- --diet <diet>` narrow it. It reads `.env`.

## Nutrition

Calories and macros (kcal, carbs, protein, fat per person's portion) are hidden until the user asks for them (F1).

- `profiles.show_nutrition` (`supabase/migrations/20261112000000_add_profile_show_nutrition.sql`, off by default, updatable by the owner only) remembers the choice on every device. `useNutritionVisibility()` reads it and saves a change; the screen follows the tap and puts the old value back, with a message, if saving fails. The migration only adds a column and can run again, so run it before deploying the app version that reads it.
- "Show nutrition" (`NutritionToggle`) is on the plan page (a round icon button on phones, a labelled button beside the title from 960 px) and on recipe detail; the plan view also has "Hide". It is one setting for both.
- Nothing is read while it is off. Once on, `useRecipeNutrition()` reads the whole library's macros once (`RECIPE_NUTRITION_COLUMNS`, paged like the recipe list) and, on a plan, the estimates of `ready` protein swaps (`recipe_protein_swaps`, locale `lt`) for the plan's recipes and its participants' diets. Both tables were already readable by signed-in users; `supabase/tests/nutrition.test.sql` covers the setting and these reads.
- The rules are pure in `shared/utils/nutrition.ts` (types in `nutrition.types.ts`), with unit tests: `getMealNutrition()` gives one meal for one participant (the recipe as written when their diet allows it; the swap's estimate when it needs a swap; the recipe's own macros, marked approximate, when the swap has no estimate or is not stored), and `getPlanNutrition()` adds up each day's planned meals and averages the days that have a total. A recipe counts only when all four values are known: three seeded recipes miss one (shown with "–"), and the plan says how many meals were left out.
- The plan page shows "Showing for" one participant at a time (the viewer when they eat from the plan, else the first participant; an individual plan is its owner's), the daily average with its macro bar (energy shares: 4 kcal per gram of carbs or protein, 9 of fat) and the notes. The day list shows each meal's macros and kcal and a total under each planned day; the week grid shows them in each cell and a row of day totals. Skipped snack slots are not counted. Recipe detail shows the four values (the swap's estimate while the user's swap is shown, D3) and the recipe list shows kcal.

## Ingredients

Every recipe item maps to a canonical ingredient with a shopping category (G1), so a shopping list can merge "Kiaušiniai" and "Kiaušiniai (M)" into one line and group lines by category.

- `public.ingredients` (`supabase/migrations/20261113000000_create_ingredients.sql`) holds the canonical name (Lithuanian, like the recipes, until X1b adds translations), the `category` and `on_shopping_list` (false only for tap water, which a list leaves out). The categories are `INGREDIENT_CATEGORIES` in `shared/utils/ingredient.ts`, in list order: `fruit_and_vegetables`, `meat_and_fish`, `dairy_and_eggs`, `grains_and_bread`, `pantry`, `frozen`, `other`; the check `ingredients_category_supported` must match (a Vitest test compares them).
- `public.ingredient_aliases` maps an item, spelled exactly as `recipe_ingredients.item` (or a protein swap's replacement) writes it, to its ingredient. Matching is exact: a new spelling is never guessed. Every canonical name is also an alias of itself, so a swap naming "Tofu" matches. Both tables are readable by signed-in users and written only by migrations (the service role), like recipes.
- The migration maps all 240 distinct seeded items to 155 ingredients, reviewed one by one. Variants of one product merge (size, dry or cooked, spelling); variants a shopper must not swap stay apart (lactose free, light or lean, whole grain, smoked, a named cheese, cherry tomatoes); a choice ("A arba B", "A / B") takes the first option; a "to taste" list of several seasonings or vegetables takes the generic "Prieskoniai", "Šviežios daržovės" or "Švieži žalumynai". Other judgment calls are commented in the migration. It is additive and re-runnable (upserts), so running it again restores the reviewed mapping.
- Unmapped items: `public.unmapped_ingredient_items` lists recipe items and ready protein swap items with no alias (service role and SQL editor only). The report, [docs/ingredient-mapping-report.md](docs/ingredient-mapping-report.md), shows them and the whole mapping by category; regenerate it with `DATABASE_URL=<connection string> npm run ingredients:report` (needs `psql`; the checked-in report comes from a fresh database with every migration applied, so it has no swaps). `supabase/tests/ingredients.test.sql` fails while a seeded recipe item has no alias, so a seed migration that adds recipes must add aliases (and ingredients) for new items.
- Unit rules (`shared/utils/ingredientUnit.ts`): amounts are added up only in the same unit, after `toBaseQuantity()` brings kg to g and l to ml. Pieces (`vnt.`) are counted on their own and never turned into grams, and so is every other unit the seed uses (skiltelė, v.š., a.š., riekelė, skardinė, pakuotė, galva, juostelės, citrinos). Spellings are tidied first (case, "vnt" without the dot, the plural "galvos"). `toDisplayQuantity()` shows 1000 g or more in kg and 1000 ml or more in l.
- To map a new item, or to correct one, add a migration that upserts into `ingredient_aliases` (and `ingredients` for a new canonical name), then regenerate the report.

## Shopping lists

Every plan has one shopping list (G2), built from its slots, participants and snack options and kept in step with them.

- Database (`supabase/migrations/20261114000000_create_shopping_lists.sql`): `shopping_lists` has one row per plan, made by a trigger when the plan is created (plans from before got theirs in the migration). `source_version` moves whenever something the list is built from changes: a slot's recipe (once per statement, so a generation moves it once; locks and notes do not), the participants (including a member leaving the household), the snack options, a participant's diet, and a protein swap of a planned recipe becoming ready or stopping being ready. The list is out of date while `generated_version` is behind it. `shopping_items` holds the lines: generated lines carry the columns a rebuild writes (`generated_key`, `ingredient_id`, `name`, `category`, `amount` and `unit` in the base unit, `is_extra`, `swapped_for`, `in_plan`); `state` (`to_buy`, `have_at_home`, `bought`), `is_removed` and `amount_override` are people's changes for G4 and G5 and are never written by a rebuild; `source = 'manual'` lines (G4) are never touched by one. Both tables are readable by whoever can open the plan (`can_access_meal_plan()`, `can_access_shopping_list()`) and not writable directly in G2.
- `apply_shopping_list_generation(target_plan_id, based_on_version, items, missing_swaps)` writes a rebuilt list. It refuses with `list_changed` when the plan changed after `based_on_version` was read, `plan_not_found` for a plan the caller cannot open, and `invalid_items` for a malformed or repeated line. Lines the plan still needs are upserted by `generated_key` (unchanged ones are not rewritten); a line it no longer needs is deleted when nobody changed it, and otherwise kept with `in_plan = false`, so bought stays bought and removed stays removed when it comes back. `supabase/tests/shopping_lists.test.sql` covers it.
- The rules are pure, in `buildShoppingList()` (`shared/utils/shoppingList.ts`, types in `shoppingList.types.ts`, unit tests next to it):
  - every planned slot counts, except snacks when the plan skips snack slots or leaves snacks off the list;
  - recipe amounts are one person's portion over the recipe's `portion_days` (a 2-day recipe's amounts feed one person on both days), so each slot takes `1 / portion_days` of the recipe per participant: a 2-day batch is counted once for both days, and a 2-day recipe on one day only (E3's "Only Tue") counts half;
  - each participant's share follows their diet: a recipe their diet does not allow uses its ready protein swap (D2) for that diet, so chicken for one and cod for another are separate lines, the swapped one saying "Swap for Monika"; without a ready swap the share follows the original recipe and the list says so (`missing_swap_count`). No AI is called;
  - items merge by canonical ingredient (G1's `ingredient_aliases`) and base unit (`toBaseQuantity()`); an item without an alias (such as an AI swap's new spelling) stays under its own spelling in "other" until it is mapped; ingredients never bought (tap water) are left out;
  - "to taste" items become extras without an amount, one per ingredient, unless the ingredient is on the list with an amount anyway.
- `POST /api/plans/<id>/shopping-list` (`refreshShoppingList()` in `server/utils/shoppingListService.ts`, tested with an in-memory store) brings the list up to date: nothing happens while it is current; otherwise it reads the plan and its list version in one request, the participants' diets, the planned recipes, their ready swaps and the aliases, all as the signed-in user (row level security decides), builds the list and writes it, building again from the changed plan up to three times on `list_changed`. It answers `200 {status: "up-to-date" | "refreshed", …}`, `409 {status: "list-changed"}` or 404.
- `/plans/<id>/list` (from "Shopping list" on the plan page, or the navigation's "List", which opens the featured plan's list through `/list`) calls it and then reads the lines (`useShoppingList()`). It shows the plan's dates and people, the lines by category in list order with amounts in the larger unit from 1000 (`toDisplayQuantity()`), the extras, and notes for snacks left off the list, a missing swap, no participants or a list that could not be brought up to date (the last version is shown). Changes by others show live (G6, below).
- Groups (G3): `getShoppingListView()` returns the groups in list order: the categories in `INGREDIENT_CATEGORIES` order, which follows a walk through a typical shop (fruit and vegetables, meat and fish, dairy and eggs, grains and bread, pantry, frozen, other), then the "to taste" extras (`EXTRAS_GROUP_KEY`); empty groups are left out. Each group (`ShoppingItemGroup.vue`) is a card whose header is a button (at least 48 px tall, `aria-expanded`, `aria-controls`) with the group's name, its line count (`itemCount`, read out as "7 items") and a chevron. All groups start open; what a viewer opens or closes is remembered per list in this browser's `localStorage` (`useShoppingListGroupExpansion()`, key `meal-planner:shopping-list-groups`, the ten most recently changed lists, read once the page is in the browser and ignored when storage is unreadable or blocked). The header takes the count as text; since G5 it reads "3 of 7" (bought of the group's lines).
- Changing the list (G4, `supabase/migrations/20261115000000_add_shopping_item_edits.sql`). There are no table grants: every change is a security definer function that checks the caller can open the plan (`can_access_shopping_list()`; `list_not_found` / `item_not_found` otherwise, the same for an unknown id) and writes one line's own fields, so two people changing different lines (G6) never overwrite each other.
  - `add_shopping_item(target_list_id, new_item_id, item_name, item_category, item_amount, item_unit)` adds a manual line (`source = 'manual'`, `added_by` the caller). The app picks the id, so a retry adds it once. Names are tidied (trimmed, inner spaces folded) and 1 to 120 characters (`invalid_name`); the category is one of `INGREDIENT_CATEGORIES` (`invalid_category`); the amount is optional, above 0 and at most 1,000,000 in its base unit (`invalid_amount`), and comes with a unit stored as a base unit: `g`, `ml`, `vnt.` or `pakuotė` (`invalid_unit`). The form offers g, kg, ml, l, pcs and pack and converts kg and l with `toBaseQuantity()`. At most 500 manual lines per list (`too_many_items`).
  - `set_shopping_item_amount(target_item_id, new_amount, new_unit)`: on a generated line it sets `amount_override` in the line's own unit (g or kg can be typed for grams; another unit is `invalid_unit`), and the plan's amount or null clears it; a "to taste" line has none (`amount_not_editable`). The override is what the person wants to buy: a rebuild never touches it, so when the plan later needs more or less the override still wins, and the line shows "Plan: 600 g" so the change is seen; "Use the plan's amount" clears it. On a manual line it sets `amount` and `unit`.
  - `set_shopping_item_state(target_item_id, new_state, new_shop_id, new_shop_name)` moves a line to `have_at_home`, `bought` (G5) or back to `to_buy`; since G7 it also writes the line's purchase (the two shop arguments are optional, see "Record the shop").
  - `remove_shopping_item(target_item_id)` marks a generated line `is_removed` (a rebuild keeps it removed; `restore_shopping_item()` brings it back) and deletes a manual one; undoing that adds it again with the same id.
  - `supabase/tests/shopping_item_edits.test.sql` covers the checks, that the changes survive `apply_shopping_list_generation()` (and are kept out of the plan, not lost, when the plan no longer needs the line), and that people outside the plan cannot use the functions.
- On the page, each line has an actions button (44 px, "Actions for Onion") with "Have at home" (or "Back to the list"), "Change amount" and "Remove"; tapping the line itself is left for G5's bought toggle. "Add item" is a round button above the navigation bar on phones and a dashed row above the groups from 960 px. Lines at home move to a "Have at home" group after the extras, closed until the viewer opens it, and are left out of the to-buy count in the header ("12 to buy · 4 at home"). Moving a line home and removing one offer "Undo" for six seconds. Changes show at once (`useShoppingItemEdits()`); when the database refuses one, the changed fields go back (unless the same field was changed again since) and a message says so (`getShoppingItemErrorKey()`). The rules for names and amounts are pure, in `shared/utils/shoppingItemEdit.ts` and `shoppingItemEdit.schema.ts`, with unit tests.
- Bought items (G5). Tapping a line ticks it bought, and tapping again unticks it; nothing is deleted. The line is a checkbox button the width of the row and at least 44 px tall (`role="checkbox"`, `aria-checked`), with a tick box as in the design; a bought line is muted with its name and amount struck through, so the strike-through is never the only signal. Ticks go through `set_shopping_item_state()` (no new database function or migration), show at once and go back with a message when refused, and calls for one line are sent one after another (`createOrderedSender()`), so two quick taps reach the database in the order they were made. Bought lines go to the bottom of their group while "Bought last" (a chip under the progress, on by default) is on; turning it off keeps name order, remembered in this browser only (`useShoppingListBoughtLast()`, `localStorage` key `meal-planner:shopping-list-bought-last`). The header shows "12 of 31 bought" with a progress bar (`role="progressbar"`) and "4 at home"; each group reads "3 of 7". Progress counts every shown line that is not at home (generated, manual and "to taste" extras alike): `getShoppingListView()` returns `boughtCount` and `totalCount`, and per group `boughtCount` and `itemCount`. Lines at home have no tick box and count neither way; a bought line can still be moved home from its menu. A rebuild never touches `state`, so a bought line stays bought when the plan's amount changes, and a bought line the plan no longer needs is kept out of the plan (hidden) and comes back bought if the plan needs it again. `supabase/tests/shopping_item_bought.test.sql` covers this.
- Shared live (G6, `supabase/migrations/20261116000000_add_shopping_list_realtime.sql`). Everyone who can open the plan sees and changes the same list: the household's members for a household plan, the owner for an individual one (G2's policies and G4's functions; nobody else can read or change it). The migration adds `shopping_lists` and `shopping_items` to the `supabase_realtime` publication (re-runnable; it does nothing when the publication is missing or already publishes every table). The list page subscribes through `useShoppingListLive()` to Realtime `postgres_changes`: its lines added or changed (filtered by `list_id`), any line deleted (Realtime sends a deleted row as its id only and cannot filter or check it against row level security, so ids the page does not show are ignored; the replica identity stays the default), and its list row. Realtime sends a row's change only to subscribers whose SELECT policies let them read it, so a member who leaves stops hearing at once. Payloads are checked with zod (`shoppingListLive.schema.ts`); one that does not parse makes the page read the list again instead. Changes from elsewhere are merged by pure functions (`shoppingListLiveMerge.ts`): a field this viewer is changing keeps the viewer's value while the call is on the way and until its echo arrives (at most three seconds after it was saved, `createShoppingItemFieldGuards()`), so another member's change to the amount shows while this viewer's tick on the same line stays; a line being added or deleted here stays added or deleted. When someone changes the plan, the list row reports `source_version` ahead of `generated_version` and every open list rebuilds itself through `POST /api/plans/<id>/shopping-list`, as on opening it (the rebuild writes only the plan's columns, so nobody's ticks are lost). The page reads the list again each time it subscribes or resubscribes (realtime-js reconnects by itself) and when the tab becomes visible, at most one read at a time (`createCoalescedRunner()`), and changes arriving during a read are applied again on top of it. Beside the title, "Live" shows while subscribed and "Reconnecting…" while not; nothing shows before the first subscription. The channel is removed when the page goes. Concurrent edits: each function locks its one line and writes its own fields, so two members changing different lines, or different fields of one line, both keep their change, and on the same field the later one wins; `supabase/tests/shopping_list_live.test.sql` covers who can read a list (what Realtime checks) and those cases, including a rebuild in between.

- Record the shop (G7, `supabase/migrations/20261117000000_create_shops_and_purchases.sql`).
  - `shops` are where people buy: a household's shops are shared by its members (for household plans and their individual plans alike); a person without a household has shops of their own. Names are tidied (trimmed, inner spaces folded, 1 to 60 characters) and `name_key` (lower case) is unique per household or person, so "LIDL" finds the "Lidl" typed first. Members read them; nobody writes the table directly.
  - `purchases` has one row per bought line (key: the line's id): `shop_id` (nullable, skipping is allowed), `bought_by`, `bought_at`, and the amount and unit the line said to buy when ticked. It exists exactly while the line is bought: `set_shopping_item_state(…, 'bought', new_shop_id, new_shop_name)` adds it in the same call (at that shop, found by name or added), moving the line back to buy or home deletes it, and a removed manual line takes it along. `set_shopping_item_shop(target_item_id, new_shop_id, new_shop_name)` sets or clears the shop of a bought line afterwards (`item_not_bought` otherwise). The app suggests the id of a shop it adds; the stored shop's id is returned (the household's shop of that name if someone added it first). Errors: `invalid_shop_name`, `too_many_shops` (200 per household), `invalid_shop`. Lines bought before the migration got a purchase without a shop. Purchases are read with the list (`can_access_shopping_list()`) and are in the `supabase_realtime` publication, so a shop shows on every open copy; `supabase/tests/shops_and_purchases.test.sql` covers it.
  - On the page, the design's "Shopping at Lidl" chip (before "Bought last"; "Choose shop" while none) opens a dialog to pick one of the household's shops, type another, or choose "No default shop". The choice lasts for this browser tab's session (`sessionStorage`, `useShoppingDefaultShop()`); while it is set, ticking a line records that shop in the same call, with no question. Without one, a saved tick shows "Onion bought · Add shop" for five seconds; ignoring it records no shop, and "Add shop" opens the same dialog for that line (tapping a shop saves it; "Use it for the next items I tick", on by default, makes it the session's shop). A bought line reads "Bought at Lidl" and its actions menu has "Add shop" / "Change shop" (with "No shop"). A bought line whose amount went up after the tick says "Needs 200 g more" (`getBoughtShortfall()`). Shops a page does not know yet (another member added one) are read again when a line names them.

### Enabling Realtime (G6)

The shopping list's live updates need Supabase Realtime with the two tables published. The G6 migration adds them to the `supabase_realtime` publication, which every Supabase project has. To check in the dashboard: Database → Publications → `supabase_realtime` lists `shopping_lists`, `shopping_items` and, since G7, `purchases` (or Table Editor → the table → "Realtime" on). Realtime must be enabled for the project (it is by default) and the browser must reach `wss://<project>.supabase.co/realtime/v1`; behind a proxy that blocks websockets the list still works and catches up when the tab comes back, showing "Reconnecting…". Nothing else is configured: no new environment variables, and no Realtime Authorization policies (the page uses `postgres_changes`, which applies the tables' row level security).

## Unit tests

Pure modules in `shared/` (such as the diet ladder and the plan generator) and the server's swap and plan generation services have Vitest tests next to them:

```bash
npm test
```

## Database tests

pgTAP tests live in `supabase/tests/`. With the Supabase CLI and a local stack (`supabase start`), run:

```bash
supabase test db
```

## Translations

UI text comes from `i18n/locales/en.json` and `i18n/locales/lt.json` through `@nuxtjs/i18n` (`no_prefix` strategy). The locale follows the browser language, falls back to English, and is remembered in a `locale` cookie. Once signed in, the language saved on the profile wins. Every key must exist in both files.
